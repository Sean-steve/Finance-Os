# ADR B0-001 — Finance OS modular monolith, ledger truth and contract-first API

**Date:** 2026-10-31  
**Status:** ACCEPTED FOR FOUNDATION ONLY (implementation choices for B1 may be revisited after live environment design).

## Decision
1. Use one independently deployable Node.js/TypeScript-compatible backend boundary (initial runtime uses native ESM JavaScript so B0 starts with minimal build complexity), PostgreSQL 16, schema migration checksum locking and OpenAPI 3.1 contracts.
2. Use a modular monolith with independent business domains and explicit API boundaries instead of deploying a microservice for each frontend screen.
3. Store financial truth in immutable, currency-balanced double-entry journals; use independently labeled staging and projection models for imports and forecast simulations.
4. Use workspace-scoped data, compound foreign keys and defense-in-depth row-level database security. Never use the migration owner for HTTP runtime user access.
5. Keep GitHub Pages static/UI-only. A successful static frontend test is **not** proof of backend authorization or financial correctness.

## Rationale
Finance OS has tightly related data across spending, banking, debt, budgeting, assets and forecasting. A unified consistent ledger avoids duplicative and eventually divergent account balances. Workspace scoping enables personal, household and business finance while retaining a single secure API. A smaller deployment footprint supports auditability and incremental integration.

## Deferred choices
- Actual identity provider, MFA and session claims design; supported bank/M-Pesa integrations; external queue and event bus; tax jurisdiction rules; distributed service separation.
- Schema migration reversible downfiles: financial ledger migrations should be forward-only, tested in disposable environments and deployed with backups/roll-forward procedures.
- Runtime framework layer may be converted to TypeScript files during B1 after contract/schema stability, without changing OpenAPI.

## Explicit risk
The B0 service is **NOT** suitable for accepting authenticated user data: no production account permissions, payments, encryption keys, secrets management or operational recovery certification are delivered yet. Database SUPERUSER or table owner bypasses RLS; production runtime credentials must be least-privileged and separately provisioned.
